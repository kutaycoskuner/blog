PostgreSQL Database Study — Migrations, Database Design, and REST API

In the next phase of the database design process, I implemented a minimal authentication system.
The system currently supports three core features:

  • Login
  • Account creation
  • Password reset/change

To avoid storing readable passwords, I also added a basic password hashing mechanism.

Since my main focus was functionality, I kept the frontend minimal while still trying to maintain a clean and aesthetically pleasing interface.

A portion of these authentication features had previously been implemented using Supabase. To avoid rewriting my existing logic, I created an authentication adapter along with an interface module, allowing the authentication layer to remain interchangeable and modular.

The first step was creating a dropdown component that fetches exercise names from the exercises table.

import { json } from '@sveltejs/kit';
import { Pool } from 'pg';
import { DATABASE_URL } from '$env/static/private';

const pool = new Pool({
	connectionString: DATABASE_URL
});

export async function GET() {
	try {
		console.log('RETRIEVE API HIT');

		const result = await pool.query('SELECT id, name FROM exercises');

		console.log('DB RESULT:', result.rows);

		return json({
			success: true,
			exercises: result.rows
		});
	} catch (err) {
		console.error('RETRIEVE ERROR FULL:', err);

		return json(
			{
				success: false,
				message: err instanceof Error ? err.message : String(err)
			},
			{ status: 500 }
		);
	}
}

Revisiting the Database Design

The next step was retrieving related data from the database.

Before implementing this part, I went back to the database design and revised the previous schema slightly.

To reduce confusion, I first categorized the table types and relationships.

Dynamic vs Static Tables

I divided the tables into two categories:

Dynamic Tables

Tables that are expected to receive active data updates over time.

For example:

  • exercises

New exercises can always be added, making this a dynamic table.

Static Tables

Tables that mainly contain reference or taxonomic data that rarely changes.

Examples include:

  • equipments
  • difficulty_levels

Even if these tables are updated in the future, the changes would happen infrequently, so I categorized them as static tables.

Relationship Types

After categorizing the tables, I analyzed the relationship structures between them.

I identified two primary relationship types.

One-to-Many Relationships

An example of this relationship is the steps table.

Each exercise can contain multiple instructional steps, but each step should only belong to a single exercise.

Many-to-Many Relationships

A good example is the relationship between exercises and tags.

  • One exercise can have multiple tags
  • One tag can belong to multiple exercises

To represent this structure properly, each many-to-many relationship must be defined through an intermediate junction table.

Naming Convention Revision

To make the relationships easier to understand visually, I revised the naming conventions used in the database schema.

Prefixes

PrefixMeaning
otm_One-to-many relationship tables
mtm_Many-to-many junction tables
ref_Static reference/taxonomy tables

Originally, I also planned to use the main_ prefix for dynamic tables containing primary data.

However, I decided against it because every templated query would require additional string manipulation logic, which would unnecessarily complicate the implementation.

Current Database Structure

The current schema structure now looks like this:


# notation: __ for meta concept separation _ used as whitespace

- exercises                     # main info
- mtm__exercises__equipments    # link table
- mtm__exercises__muscles       # link table
- mtm__exercises__tags          # beginner friendly, ...
- otm__exercises__steps         # how to do steps for exercise
- otm__exercises__media         # visuals, gifs, video
- ref__difficulty_levels        # beginner, intermediate, hard ...
- ref__equipments               # bars, parallets, dumnbells, ...
- ref__exercise_types           # calisthenics, strength, posture, ...
- ref__muscle_groups            # back, core ...
- ref__muscles                  # rhomboids, deltoid, ...
- tags                          # tags
- users                         # for authentication

Fetching Related Exercise Data

The next step was creating an API endpoint capable of retrieving related data based on the selected exercise from the dropdown.

The flow works like this:

  1. The user selects an exercise from the dropdown
  2. The frontend retrieves the exercise’s unique identifier
  3. The identifier is sent to the API endpoint

The new endpoint structure is:

/api/test/retrieve/exercise/[id]/+server.ts
import { json } from '@sveltejs/kit';
import { Pool } from 'pg';
import { DATABASE_URL } from '$env/static/private';
import type { RequestHandler } from './$types';

const pool = new Pool({
    connectionString: DATABASE_URL
});

export const GET: RequestHandler = async ({ params }) => {
    const exerciseId = params.id;

    try {
        console.log(`RETRIEVE EXERCISE DATA FOR ID: ${exerciseId}`);

        const query = `
            SELECT 
                e.id, 
                e.name,
                e.description,
                -- Aggregate primary muscles from ref__muscles
                COALESCE(
                    ARRAY_AGG(DISTINCT m.name) FILTER (WHERE m.name IS NOT NULL AND mem.type = 'primary'), 
                    '{}'
                ) AS primary_muscles,
                -- Aggregate secondary muscles from ref__muscles
                COALESCE(
                    ARRAY_AGG(DISTINCT m.name) FILTER (WHERE m.name IS NOT NULL AND mem.type = 'secondary'), 
                    '{}'
                ) AS secondary_muscles,
                -- JOINED to public.tags to grab the simple text 'name' column
                COALESCE(
                    ARRAY_AGG(DISTINCT t.name) FILTER (WHERE t.name IS NOT NULL), 
                    '{}'
                ) AS tags,
                -- Aggregate media attachments from the otm table
                COALESCE(
                    JSON_AGG(DISTINCT jsonb_build_object('type', oem.type, 'url', oem.url)) FILTER (WHERE oem.id IS NOT NULL), 
                    '[]'
                ) AS media
            FROM exercises e
            LEFT JOIN mtm__exercises__muscles mem ON e.id = mem.exercise_id
            LEFT JOIN ref__muscles m ON mem.muscle_id = m.id
            -- Junction table to link exercises to tags
            LEFT JOIN mtm__exercises__tags mt ON e.id = mt.exercise_id
            -- Direct link to your public.tags table to swap ID for Name
            LEFT JOIN public.tags t ON mt.tag_id = t.id
            LEFT JOIN otm__exercises__media oem ON e.id = oem.exercise_id
            WHERE e.id = $1
            GROUP BY e.id;
        `;

        const result = await pool.query(query, [exerciseId]);

        // 404 handler if record is missing
        if (result.rows.length === 0) {
            return json(
                { success: false, message: 'Exercise not found' },
                { status: 404 }
            );
        }

        // Return clean payload
        return json({
            success: true,
            exercise: result.rows[0]
        });

    } catch (err) {
        console.error(`ERROR RETRIEVING EXERCISE ${exerciseId}:`, err);
        return json(
            {
                success: false,
                message: err instanceof Error ? err.message : String(err)
            },
            { status: 500 }
        );
    }
};

Handling Images

The next step involved loading exercise images.

However, after researching the topic, I learned that storing binary image files directly inside the database is generally not considered a good approach for this type of application.

For now, I decided to only store image paths instead of the actual binary files.
